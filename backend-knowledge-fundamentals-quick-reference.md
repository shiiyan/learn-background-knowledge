| 1 | <a id="q-01-https-request-lifecycle"></a>**HTTPS Request Lifecycle**<br>**EN:** What happens when a client sends an HTTPS request?<br>**日本語:** ClientがHTTPS requestを送ると何が起きますか？ | DNSでdomainをIPへ解決し、TCPまたはQUIC connectionを作り、TLSで相手を検証して暗号化します。Requestはload balancer/reverse proxyを経てbackendへ届き、validation、business logic、data accessの後にresponseが返ります。<br>**Example / 例:** `api.example.com`を解決し、TLS後に`GET /users/42`を送ります。<br>**Keywords:** DNS, TCP, QUIC, TLS, proxy, backend | **EN:** Where can latency or failure occur?<br>**日本語:** どこでlatencyやfailureが起きますか？ | DNS、connection/TLS setup、proxy queue、application、DB、downstreamごとに起きます。Timeoutとtrace spanを段階別に置くと切り分けできます。<br>**Example / 例:** Traceで900ms中DBが800msと特定します。<br>**Keywords:** latency breakdown, timeout, trace |
| 2 | <a id="q-02-http-messages-and-semantics"></a>**HTTP Messages and Semantics**<br>**EN:** What are the parts of HTTP requests and responses, and how do methods and status codes work?<br>**日本語:** HTTP messageの要素とmethod/status codeを説明してください。 | Requestはmethod、target、headers、任意のbody、responseはstatus、headers、任意のbodyです。GETは取得、POSTは作成/処理、PUTは全体置換、PATCHは部分更新、DELETEは削除です。2xxは成功、4xxはclient側、5xxはserver側問題です。<br>**Example / 例:** JSON POSTへ`201 Created`を返します。<br>**Keywords:** method, URL, header, body, status | **F1 — EN:** How do 400, 401, 403, 404, 409, and 422 differ?<br>**F1 — 日本語:** 400、401、403、404、409、422はどう違いますか？<br><br>**F2 — EN:** What do Content-Type and Accept mean?<br>**F2 — 日本語:** Content-TypeとAcceptとは？ | **A1:** 400は不正request、401は認証不足、403は権限不足、404は不存在、409はstate競合、422はsemantic validation失敗です。<br>**A2:** `Content-Type`は実際のbody形式、`Accept`はclientが受け取れる形式です。<br>**Example / 例:** Duplicate emailは409、field rule違反は422にできます。<br>**Keywords:** authentication, authorization, conflict, content negotiation |
| 3 | <a id="q-03-http-versions-tcp-and-udp"></a>**HTTP Versions, TCP, and UDP**<br>**EN:** How do TCP, UDP, HTTP/1.1, HTTP/2, and HTTP/3 differ?<br>**日本語:** TCP、UDP、HTTP/1.1、HTTP/2、HTTP/3の違いは？ | TCPは信頼できるordered byte stream、UDPはdelivery/orderを保証しないdatagram transportです。HTTP/1.1/2はTCPを使い、HTTP/2はstreamをmultiplexします。HTTP/3はQUIC/UDP上でstream単位のloss isolationを得ます。<br>**Example / 例:** HTTP/2は一connectionで複数requestを並行処理します。<br>**Keywords:** stream, datagram, multiplexing, QUIC | **F1 — EN:** How does TCP establish reliable delivery?<br>**F1 — 日本語:** TCPはどうconnectionとreliabilityを確立しますか？<br><br>**F2 — EN:** Why reuse HTTP clients and connections?<br>**F2 — 日本語:** HTTP client/connectionを再利用する理由は？ | **A1:** Three-way handshake後、sequence number、ACK、retransmission、flow/congestion controlでordered deliveryを提供します。<br>**A2:** TCP/TLS setup、latency、CPU、ephemeral port消費を減らします。Idle limitとtimeoutも必要です。<br>**Example / 例:** Requestごとにnew clientを作らずshared poolを使います。<br>**Keywords:** SYN, ACK, retransmission, keep-alive, pool |
| 4 | <a id="q-04-dns-and-tls"></a>**DNS and TLS**<br>**EN:** How do DNS resolution and the TLS handshake work?<br>**日本語:** DNS resolutionとTLS handshakeはどう動作しますか？ | Resolverはcache miss時にroot、TLD、authoritative serverを辿り、A/AAAA等をTTL付きで返します。TLS 1.3ではparameters/key shareを交換し、clientがcertificate chain、hostname、署名を検証し、shared secretからsymmetric keysを導出します。<br>**Example / 例:** `api.example.com`のA record取得後、certificateを検証します。<br>**Keywords:** resolver, authoritative, TTL, certificate, ECDHE | **F1 — EN:** What are A, AAAA, CNAME, MX, NS, and TXT records?<br>**F1 — 日本語:** 主なDNS recordは？<br><br>**F2 — EN:** Where is TLS terminated, and when is mTLS useful?<br>**F2 — 日本語:** TLS terminationとmTLSを説明してください。 | **A1:** A/AAAAはaddress、CNAMEはalias、MXはmail、NSはnameserver、TXTはmetadataです。TTL cacheにより変更反映は段階的です。<br>**A2:** LB/proxyで終端でき、内部を再暗号化できます。mTLSは双方のservice identityをcertificateで確認します。<br>**Example / 例:** ALBで終端しservice間はmTLSにします。<br>**Keywords:** DNS records, propagation, termination, mTLS |
| 5 | <a id="q-05-rest-sessions-and-identity"></a>**REST, Sessions, and Identity**<br>**EN:** What are a RESTful endpoint, statelessness, authentication, and authorization?<br>**日本語:** REST endpoint、statelessness、authentication、authorizationとは？ | Endpointはmethod/path/contractで定義されます。RESTはresource、HTTP semantics、statelessnessを一貫して使います。Authenticationはidentity確認、authorizationはresource/actionへのpermission判定です。Session ID+shared storeまたはtokenでlogin stateを表します。<br>**Example / 例:** Login済みでも他userのorder取得は拒否します。<br>**Keywords:** REST, endpoint, stateless, identity, permission | **F1 — EN:** Which cookie attributes matter?<br>**F1 — 日本語:** 重要なcookie属性は？<br><br>**F2 — EN:** How do JWT, opaque tokens, OAuth 2.0, and OIDC differ?<br>**F2 — 日本語:** JWT、opaque token、OAuth 2.0、OIDCの違いは？ | **A1:** Secure、HttpOnly、SameSite、Domain、Path、expiryがtransport、script access、cross-site送信、scopeを制御します。<br>**A2:** JWTはsigned claimsを自己検証、opaque tokenはserver-side lookup向きです。OAuthはdelegated authorization、OIDCはidentity layerです。<br>**Example / 例:** OAuthでAPI access、OIDCでuser identityを得ます。<br>**Keywords:** cookie, JWT, revocation, OAuth, OIDC |
| 6 | <a id="q-06-idempotency-and-remote-call-resilience"></a>**Idempotency and Remote-Call Resilience**<br>**EN:** How do you make remote operations safe and bounded?<br>**日本語:** Remote operationを安全かつboundedにするには？ | 全callへdeadline/timeoutを設定し、一時的で安全なfailureだけをbounded retryします。Side effectにはidempotency key/deduplication、連続failureにはcircuit breakerを使います。<br>**Example / 例:** Payment POSTを同じkeyでretryしてもchargeは一件だけです。<br>**Keywords:** timeout, retry, idempotency, circuit breaker | **F1 — EN:** How does an idempotency key work?<br>**F1 — 日本語:** Idempotency keyはどう動作しますか？<br><br>**F2 — EN:** Which errors should be retried, and why use backoff and jitter?<br>**F2 — 日本語:** 何をretryし、なぜbackoff+jitterを使いますか？ | **A1:** Key、request fingerprint、processing state、resultをatomicに保存し、同key/same payloadへ元の結果を返します。異なるpayloadは拒否します。<br>**A2:** Timeout、429、一部5xxなどtransient failureだけをretryします。Exponential backoff+jitterで同期retry stormを防ぎます。<br>**Example / 例:** 400はretryせず503を最大3回retryします。<br>**Keywords:** fingerprint, unique constraint, transient error, retry storm |
| 7 | <a id="q-07-proxies-load-balancers-and-api-gateways"></a>**Proxies, Load Balancers, and API Gateways**<br>**EN:** How do a forward proxy, reverse proxy, load balancer, and API gateway differ?<br>**日本語:** Forward proxy、reverse proxy、load balancer、API gatewayの違いは？ | Forward proxyはclientを代表、reverse proxyはserver群を代表します。Load balancerはhealthy backendへtrafficを分散し、API gatewayはroutingに加えauthentication、quota、transformation等のAPI policyを提供します。機能は製品ごとに重なります。<br>**Example / 例:** ALBがhealthy podsへ分散しgatewayがtokenとquotaを検証します。<br>**Keywords:** forward proxy, reverse proxy, load balancer, API gateway | **EN:** Why must forwarded headers and health checks be handled carefully?<br>**日本語:** Forwarded headerとhealth checkの注意点は？ | Trusted proxy以外の`X-Forwarded-*`を信じるとIP/scheme spoofingになります。Health checkはprocess生存だけでなくtrafficを安全に受けられるかを判定し、過剰なdependency checkで全backendを外さないようにします。<br>**Example / 例:** Appはknown LBからのforwarded headerだけを採用します。<br>**Keywords:** trusted proxy, spoofing, health check |
| 8 | <a id="q-08-http-caching-and-conditional-requests"></a>**HTTP Caching and Conditional Requests**<br>**EN:** How do HTTP caching and conditional requests work?<br>**日本語:** HTTP cacheとconditional requestはどう動作しますか？ | `Cache-Control`でfreshnessとstorage scopeを指定し、ETag/Last-Modifiedをvalidatorとして`If-None-Match`/`If-Modified-Since`で再検証します。変更がなければ304でbody送信を省けます。<br>**Example / 例:** Public articleを60秒cacheしETagで再検証します。<br>**Keywords:** Cache-Control, ETag, validator, 304 | **EN:** How do no-cache, no-store, private, and Vary differ?<br>**日本語:** no-cache、no-store、private、Varyの違いは？ | `no-cache`は保存可だが利用前に再検証、`no-store`は保存禁止、`private`はshared cache禁止です。`Vary`はどのrequest headerごとに別cache entryを持つか示します。<br>**Example / 例:** Personalized responseを`private`にします。<br>**Keywords:** freshness, shared cache, Vary |

| 10 | <a id="q-10-joins-normalization-and-orms"></a>**Joins, Normalization, and ORMs**<br>**EN:** What are joins, normalization, denormalization, and ORMs?<br>**日本語:** Join、normalization、denormalization、ORMとは？ | JOINはrelated rowsを結合します。Normalizationは重複/update anomalyを減らし、denormalizationはreadを簡単にする代わりstaleness/update costを増やします。ORMはobject-table mappingを簡単にしますがSQLを隠し得ます。<br>**Example / 例:** Order/itemを正規化しdashboard summaryをdenormalizeします。<br>**Keywords:** JOIN, normalization, redundancy, ORM | **EN:** What is N+1, and how do you fix it?<br>**日本語:** N+1 problemと対策は？ | Parentを1 query、各childをN queryで読む問題です。Query log/traceで検出し、join、batch、eager loadingを使います。Over-fetchingにも注意します。<br>**Example / 例:** 100 user IDsのordersを一つのIN queryで取得します。<br>**Keywords:** N+1, lazy loading, batching |

| 12 | <a id="q-12-postgresql-mvcc-vacuum-and-wal"></a>**PostgreSQL MVCC, VACUUM, and WAL**<br>**EN:** How do PostgreSQL MVCC, VACUUM, and WAL work?<br>**日本語:** PostgreSQLのMVCC、VACUUM、WALはどう動作しますか？ | MVCCはrow versionとsnapshotでreader/writerのblockingを減らします。UPDATE/DELETE後のdead tupleはVACUUMが再利用可能にします。WALはdata pageより先にchange recordを書き、crash recovery、replication、PITRに使います。<br>**Example / 例:** UPDATEはnew tupleを作り、後でVACUUMがold versionを回収します。<br>**Keywords:** MVCC, snapshot, dead tuple, VACUUM, WAL | **EN:** How can a long transaction harm PostgreSQL?<br>**日本語:** Long transactionはPostgreSQLへどう影響しますか？ | Old snapshotがtuple回収を妨げ、table/index bloat、storage増加、transaction-ID riskを高めます。`idle in transaction`も監視します。<br>**Example / 例:** Long report transactionがautovacuum progressを妨げます。<br>**Keywords:** autovacuum, bloat, long transaction |

| 14 | <a id="q-14-mysql-innodb-indexes-and-locking"></a>**MySQL/InnoDB Indexes and Locking**<br>**EN:** How do InnoDB clustered/secondary indexes and optimistic/pessimistic locking work?<br>**日本語:** InnoDB indexとoptimistic/pessimistic lockを説明してください。 | InnoDB tableはprimary keyのclustered indexにrowを置き、secondary index leafはprimary keyを参照するため、小さくstableなprimary keyが有利です。Optimistic lockingはversion checkでconflictを検出、pessimistic lockingは`SELECT ... AND version=?`でlost updateを防ぎます。<br>**Keywords:** InnoDB, clustered index, secondary index, optimistic locking | **EN:** When should each locking strategy be used?<br>**日本語:** 各locking strategyをいつ使いますか？ | Conflictがrareでretry可能ならoptimistic、conflictが多く短いcritical sectionを確実に直列化するならpessimisticを検討します。Pessimistic lockはwait/deadlockを増やします。<br>**Example / 例:** Low-contention profile編集はversion check、在庫確保はrow lockを検討します。<br>**Keywords:** version column, FOR UPDATE, contention |
