| 1 | <a id="q-01-api-endpoint"></a>**API Endpoint**<br>**EN:** What is an API endpoint?<br>**日本語:** API endpointとは何ですか？ | Clientが特定のresourceやoperationへアクセスする入口です。通常はHTTP method、path、request/response contractの組み合わせで定義します。例えば、`POST /reservations`は予約を作成するendpointです。<br>**Example / 例:** `GET /users/42` はuser 42を取得する一つのendpointです。<br>**Keywords:** API endpoint, resource, operation, HTTP method, path, request, response, contract | **F1 — EN:** What should you consider when designing a good API endpoint?<br>**F1 — 日本語:** 良いAPI endpointを設計するとき、何を考慮しますか？<br><br>**F2 — EN:** How should an API return errors consistently?<br>**F2 — 日本語:** APIのerror responseをどのように統一しますか？ | **A1:** Resource naming、HTTP methodとstatus code、input validation、authentication/authorization、idempotency、error format、versioning、observabilityを考慮します。実装方法より先に、clientとのcontractを明確にします。<br>**Example / 例:** `POST /orders` が成功したら `201 Created` と作成resourceのlocationを返します。<br>**Keywords:** resource naming, HTTP semantics, validation, authorization, idempotency, error model, versioning, observability<br><br>**A2:** HTTP statusだけでなく、安定したmachine-readable error code、user-safe message、必要なdetails、correlation IDを共通schemaで返します。Internal stack traceやsecretは公開せず、clientがretry可能か判断できる情報を示します。<br>**Example / 例:** Invalid emailなら `400`、`code: VALIDATION_ERROR`、`request_id` を返します。<br>**Keywords:** error schema, error code, HTTP status, correlation ID, retryability, information disclosure |
| 2 | <a id="q-02-restful-api"></a>**RESTful API**<br>**EN:** What is a RESTful API?<br>**日本語:** RESTful APIとは何ですか？ | ResourceをURIで表現し、HTTP methodのsemanticsを利用するstatelessなAPI設計です。Uniform interface、cacheability、layered systemなどの制約があります。単にJSONを返すHTTP APIという意味ではありません。<br>**Example / 例:** `GET /articles/10` でarticleを取得し、`DELETE /articles/10` で同じresourceを削除します。<br>**Keywords:** REST, resource, URI, stateless, uniform interface, cacheability, layered system | **F1 — EN:** How would you choose between REST and RPC or gRPC?<br>**F1 — 日本語:** RESTとRPCまたはgRPCをどう使い分けますか？<br><br>**F2 — EN:** What does HATEOAS mean, and is it always necessary?<br>**F2 — 日本語:** HATEOASとは何で、常に必要ですか？ | **A1:** Publicまたはresource-orientedなAPIではRESTが扱いやすいことが多いです。Internal service間で厳密なschema、code generation、低latency、streamingが重要ならgRPCが有力です。Client compatibility、debuggability、browser support、運用経験も判断材料です。<br>**Example / 例:** Public mobile APIはREST、内部のhigh-throughput recommendation callはgRPCを選ぶ例があります。<br>**Keywords:** REST, RPC, gRPC, schema, code generation, streaming, compatibility, latency, debuggability<br><br>**A2:** Responseに次に実行可能なactionへのlinkを含め、clientがserverから状態遷移を発見できる考え方です。RESTの重要な制約ですが、実務ではclientの単純さ、API maturity、組織の規約を考慮し、全APIで完全実装するとは限りません。<br>**Example / 例:** Orderが未払いならresponseに `pay`、発送済みなら `track` linkを含めます。<br>**Keywords:** HATEOAS, hypermedia, link relation, discoverability, REST constraint |
| 3 | <a id="q-03-https-request-response-cycle"></a>**HTTPS Request/Response Cycle**<br>**EN:** Describe a typical HTTPS request/response cycle.<br>**日本語:** HTTPS requestがclientからserverへ届き、responseが返るまでを説明してください。 | 一般的には、DNS名前解決、connection確立、TLS handshake、HTTP request送信、load balancerやreverse proxy、application処理、databaseやdownstream serviceへのアクセス、HTTP responseという順に進みます。Connectionはkeep-aliveやpoolingによって再利用される場合があります。<br>**Example / 例:** BrowserでHTTPS pageを開くと、DNS解決後にsecure connectionを作り、`GET` がload balancer経由でapplicationへ届きます。<br>**Keywords:** DNS, TCP, QUIC, TLS handshake, HTTP, load balancer, reverse proxy, connection reuse | **F1 — EN:** How would you investigate a slow request?<br>**F1 — 日本語:** このrequestが遅い場合、どこから調査しますか？<br><br>**F2 — EN:** Is TLS outdated, and does HTTPS always establish TCP before TLS?<br>**F2 — 日本語:** TLSは古い技術ですか？ またHTTPSでは常にTLSの前にTCP connectionを確立しますか？<br><br>**F3 — EN:** Where is TLS usually terminated?<br>**F3 — 日本語:** TLSは通常どこでterminationされますか？ | **A1:** まず影響範囲とlatency breakdownを確認します。DNS、connection、TLS、load balancer、application、database、downstream dependencyの順に、metrics、logs、distributed tracesを使ってbottleneckを特定します。直近のdeployやtraffic変化も確認します。<br>**Example / 例:** Traceを見ると全体900msのうちdatabase spanが800msで、slow queryがbottleneckだと分かります。<br>**Keywords:** latency breakdown, metrics, logs, traces, bottleneck, dependency, recent deployment<br><br>**A2:** いいえ。古いのはSSLで、modern HTTPSは通常TLS 1.2またはTLS 1.3を使います。HTTP/1.1とHTTP/2では通常 `DNS → TCP → TLS → HTTP`、HTTP/3では `DNS → QUIC/UDP（TLS 1.3を統合）→ HTTP/3` です。したがってTCPが先という説明はHTTP/3には当てはまりません。<br>**Example / 例:** HTTP/2接続ではTCPとTLS、HTTP/3接続ではQUIC/UDPと統合TLS 1.3を使います。<br>**Keywords:** SSL, TLS 1.2, TLS 1.3, TCP, QUIC, UDP, HTTP/2, | 4 | <a id="q-04-idempotency"></a>**Idempotency**<br>**EN:** What is idempotency?<br>**日本語:** Idempotencyとは何ですか？ | 同じoperationを複数回実行しても、最終的なbusiness outcomeが変わらない性質です。HTTP semanticsではGET、PUT、DELETEは原則idempotentですが、POSTは通常idempotentではありません。<br>**Example / 例:** 同じ `DELETE /users/42` を二回送っても、user 42が削除済みという最終状態は同じです。<br>**Keywords:** idempotency, duplicate request, retry, business outcome, HTTP semantics | **F1 — EN:** How would you safely retry a reservation or payment POST request?<br>**F1 — 日本語:** 予約作成や決済のPOSTを安全にretryするにはどうしますか？<br><br>**F2 — EN:** How long should an idempotency key be stored?<br>**F2 — 日本語:** Idempotency keyをどのくらい保存しますか？ | **A1:** Clientが一意なidempotency keyを送り、server側でkey、request identity、処理状態、resultを保存します。同じkeyの再送では処理を再実行せず、保存済みの結果を返します。Databaseのunique constraintやreconciliationも併用します。<br>**Example / 例:** Payment requestを同じkeyで再送すると、新しいchargeではなく最初のcharge IDを返します。<br>**Keywords:** idempotency key, request identity, stored result, unique constraint, retry safety, reconciliation<br><br>**A2:** Clientのretry window、operationの完了時間、business riskに基づいてretentionを決めます。同じkeyで異なるpayloadが来た場合を検出するためrequest hashも保存し、期限切れ後の再実行が許容できるか明確にします。<br>**Example / 例:** Clientが24時間retryする契約ならkeyを24時間以上保持する、という決め方があります。<br>**Keywords:** retention window, request hash, payload mismatch, retry window, expiration |
| 5 | <a id="q-05-http-statelessness"></a>**HTTP Statelessness**<br>**EN:** What does statelessness mean in HTTP?<br>**日本語:** HTTPがstatelessであるとはどういう意味ですか？ | 各requestは独立しており、serverが以前のrequestを覚えていることをprotocolとして前提にしないという意味です。必要な状態はtoken、database、session storeなど、application側で明示的に管理します。<br>**Example / 例:** Authorization tokenと共有databaseがあれば、同じrequestをどのapplication instanceでも処理できます。<br>**Keywords:** stateless, independent request, application state, session, token, horizontal scaling | **F1 — EN:** How would you manage sessions in a load-balanced environment?<br>**F1 — 日本語:** Load-balanced environmentでsessionをどう管理しますか？<br><br>**F2 — EN:** Does statelessness mean a backend cannot use a database or server-side state?<br>**F2 — 日本語:** Statelessとはdatabaseやserver-side stateを使えないという意味ですか？ | **A1:** Application instanceをstatelessにし、sessionをRedisなどの共有storeへ保存する方法が一般的です。Sticky sessionも利用できますが、load distribution、failover、scalingが難しくなる場合があります。Token-based方式ではrevocationやtoken sizeなども考慮します。<br>**Example / 例:** 三つのapplication podが同じRedis session storeを参照します。<br>**Keywords:** centralized session store, Redis, sticky session, token, failover, horizontal scaling<br><br>**A2:** いいえ。各requestを処理するためのcontextがrequestまたは共有data storeから取得でき、特定application instanceの過去の会話状態に依存しないという意味です。Persistent business dataやshared session storeは利用できます。<br>**Example / 例:** Product dataをdatabaseへ保存するのは問題ありませんが、cartを一台のinstance memoryだけに置くとstatelessではありません。<br>**Keywords:** stateless request, instance-local state, persistent state, shared store, request context |
| 6 | <a id="q-06-api-versioning"></a>**API Versioning**<br>**EN:** How do you version an API?<br>**日本語:** API versioningをどのように行いますか？ | まずbackward-compatibleなadditive changeを優先します。Breaking changeが必要な場合はURLやheaderなどでversionを分け、migration period、deprecation policy、usage monitoringを用意します。<br>**Example / 例:** Optionalな `avatar_url` 追加はv1のまま、既存fieldの意味変更はv2として提供します。<br>**Keywords:** API versioning, backward compatibility, additive change, breaking change, deprecation, migration | **F1 — EN:** How would you evolve an event schema without breaking consumers?<br>**F1 — 日本語:** Consumerを壊さずにevent schemaを変更するにはどうしますか？<br><br>**F2 — EN:** When should you avoid creating a new API version?<br>**F2 — 日本語:** 新しいAPI versionを作らない方がよいのはいつですか？ | **A1:** Optional fieldの追加などbackward/forward compatibilityを保つ変更を優先します。Schema registry、versioned contract、consumer-driven testを利用し、producerとconsumerを段階的に移行します。Fieldの意味を変更したり、すぐ削除したりしません。<br>**Example / 例:** Order eventへoptionalな `currency` fieldを追加し、old consumerは無視できるようにします。<br>**Keywords:** schema evolution, backward compatibility, forward compatibility, schema registry, consumer-driven contract, gradual migration<br><br>**A2:** Optional field追加、新endpoint追加、既存semanticsを変えない拡張など、backward-compatibleに進化できる場合です。Versionを増やすとdocumentation、testing、support、retirementのcostが増えるため、breaking changeに限定します。<br>**Example / 例:** Optional filterの追加だけなら `/v2` を新設せず、既存versionを拡張します。<br>**Keywords:** additive change, backward compatibility, version sprawl, maintenance cost, breaking change |
| 9 | <a id="q-09-file-uploads"></a>**File Uploads**<br>**EN:** How would you handle file uploads in a web application?<br>**日本語:** Web applicationでfile uploadをどう設計しますか？ | Size、file type、contentの検証、authorization、unique object key、quota、malware scan、metadata管理を行います。大きなfileはapplication serverに全て読み込まず、object storageへのdirect uploadやstreamingを検討します。<br>**Example / 例:** Image upload用presigned URLを発行し、applicationはfile本体ではなくmetadataを管理します。<br>**Keywords:** object storage, presigned URL, streaming, validation, authorization, quota, malware scanning | **F1 — EN:** How would you upload a multi-gigabyte file without overloading the backend?<br>**F1 — 日本語:** 数GBのfileをuploadする場合、backend負荷をどう抑えますか？<br><br>**F2 — EN:** What if the filename extension and Content-Type disagree?<br>**F2 — 日本語:** Filename extensionとContent-Typeが一致しない場合はどうしますか？ | **A1:** Presigned URLを発行してclientからobject storageへmultipart uploadさせます。Backendはauthorizationとmetadataを管理し、upload完了後のvalidationやscanをasynchronous jobとして実行します。Retry可能なpart単位に分割します。<br>**Example / 例:** 5GB fileを100MBのpartに分けてobject storageへ直接uploadし、失敗partだけretryします。<br>**Keywords:** presigned URL, multipart upload, object storage, asynchronous processing, retry, metadata<br><br>**A2:** どちらもclient-controlledとして信用せず、magic bytesや実際のcontentを検査します。隔離領域へ保存してmalware scanや必要なre-encodingを行い、実行可能pathから分離します。不明または危険な形式は拒否します。<br>**Example / 例:** `.jpg` という名前でも実体がexecutableなら検査で拒否します。<br>**Keywords:** magic bytes, MIME sniffing, quarantine, malware scan, re-encoding, untrusted input |

| 11 | <a id="q-11-sql-vs-nosql-databases"></a>**SQL vs. NoSQL Databases**<br>**EN:** What is the difference between SQL and NoSQL databases?<br>**日本語:** SQL databaseとNoSQL databaseの違いは何ですか？ | SQL databaseはtable、relation、SQL、transactionを中心とし、複雑なqueryや強い整合性に向いています。NoSQLはkey-value、document、wide-column、graphなど複数のmodelがあり、access pattern、柔軟なschema、水平分散を重視する場合に有力です。名前だけで選ばず、data modelと要件で判断します。<br>**Example / 例:** OrderとtransactionにはPostgreSQL、session cacheにはRedis、relationship traversalにはgraph databaseを選ぶ例があります。<br>**Keywords:** relational database, NoSQL, schema, transaction, join, access pattern, horizontal scaling | **F1 — EN:** When would you choose a NoSQL database over a relational database?<br>**F1 — 日本語:** Relational databaseではなくNoSQLを選ぶのはどのような場合ですか？<br><br>**F2 — EN:** Can a NoSQL database provide ACID transactions?<br>**F2 — 日本語:** NoSQL databaseでもACID transactionを提供できますか？ | **A1:** 単純で明確なaccess pattern、大量の分散write、柔軟なdocument構造、またはgraph traversalなど、特定のNoSQL modelが要件に合う場合です。Transaction、join、consistency、運用経験を犠牲にしてよいかも確認します。<br>**Example / 例:** 大量eventをdevice ID単位で分散writeするworkloadではwide-column storeが候補です。<br>**Keywords:** workload, access pattern, scale, consistency, transaction, data model, operational maturity<br><br>**A2:** はい。多くのNoSQL製品がtransactionを提供しますが、単一item、partition内、複数documentなど保証範囲とcostが異なります。SQL対NoSQLをACIDの有無だけで分類せず、実際のconsistencyとtransaction semanticsを確認します。<br>**Example / 例:** Document databaseがmulti-document transactionを提供しても、単一document updateよりcostが高い場合があります。<br>**Keywords:** ACID, transaction scope, partition, consistency guarantee, NoSQL |
