| 1 | <a id="q-01-jvm-execution-pipeline"></a>**JVM Execution Pipeline**<br>**EN:** How does Java code execute on the JVM?<br>**日本語:** Java codeはJVM上でどのように実行されますか？ | Java sourceはcompilerでbytecodeになり、class loaderがJVMへload・link・initializeします。最初はinterpreterで実行され、頻繁に通るcodeはJIT compilerがnative codeへ最適化します。<br>**Example / 例:** 同じloopが何度も実行されるとhot methodとしてJIT compileされます。<br>**Keywords:** bytecode, class loader, interpreter, JIT, native code | **F1 — EN:** What does the class loader do?<br>**F1 — 日本語:** Class loaderは何をしますか？<br><br>**F2 — EN:** Why can JVM performance improve after startup?<br>**F2 — 日本語:** JVMは起動後にperformanceが向上することがあるのはなぜですか？ | **A1:** Classを必要時に読み込み、verification、linking、initializationを行います。Parent delegationによりcore classの置換を防ぎます。<br>**Example / 例:** ApplicationClassLoaderがservice classをloadする前にparentへjava.lang.Stringを問い合わせます。<br>**Keywords:** class loading, verification, linking, initialization, parent delegation<br><br>**A2:** Runtime profileからhot pathを見つけ、JITがinliningやspeculative optimizationを行うためです。前提が崩れるとdeoptimizationも起こります。<br>**Example / 例:** Benchmark直後よりwarm-up後のthroughputが高くなります。<br>**Keywords:** warm-up, profiling, inlining, speculative optimization, deoptimization |
| 2 | <a id="q-02-jvm-heap-stack-and-object-lifetime"></a>**JVM Heap, Stack, and Object Lifetime**<br>**EN:** What is stored in JVM heap and thread stacks?<br>**日本語:** JVMのheapとthread stackには何が保存されますか？ | Objectとarrayは通常heapに置かれ、全threadから参照され得ます。各thread stackにはmethod frame、local variable、operand stack、return情報が置かれます。Objectが到達不能になるとGC対象です。<br>**Example / 例:** `new User()` のobjectはheap、method内のreferenceとprimitive local variableはstack frameに置かれます。<br>**Keywords:** heap, thread stack, stack frame, object allocation, reachability | **F1 — EN:** Can a Java object ever avoid heap allocation?<br>**F1 — 日本語:** Java objectがheap allocationを避けることはありますか？<br><br>**F2 — EN:** What commonly causes OutOfMemoryError?<br>**F2 — 日本語:** OutOfMemoryErrorの主な原因は何ですか？ | **A1:** JITのescape analysisにより、thread外へescapeしないallocationをscalar replacementで除去できる場合があります。Language levelでstack allocationを保証するわけではありません。<br>**Example / 例:** 短命なPoint objectが最適化後は二つのscalar valueとして扱われます。<br>**Keywords:** escape analysis, scalar replacement, allocation elimination<br><br>**A2:** Live object増加、unbounded cache、large allocation、Metaspace増加、native/direct memory不足などです。Heap dumpとmemory metricで種類とretaining pathを確認します。<br>**Example / 例:** TTLのないMapがrequestごとにentryを保持しheapを使い切ります。<br>**Keywords:** OutOfMemoryError, heap dump, retained object, Metaspace, direct memory |

| 9 | <a id="q-09-acid-transactions"></a>**ACID Transactions**<br>**EN:** What do ACID properties mean in practice?<br>**日本語:** ACID propertyを実務的に説明してください。 | Atomicityは全成功か全失敗、Consistencyは定義したinvariant維持、Isolationはconcurrent transactionの干渉制御、Durabilityはcommit済みdataの永続化です。各保証にはdatabase設定とapplication設計が必要です。<br>**Example / 例:** 送金ではdebitとcreditを同じtransactionにし、途中失敗なら両方rollbackします。<br>**Keywords:** ACID, atomicity, consistency, isolation, durability, invariant | **F1 — EN:** Does ACID consistency mean the same thing as CAP consistency?<br>**F1 — 日本語:** ACIDのConsistencyとCAPのConsistencyは同じですか？<br><br>**F2 — EN:** When should a transaction be kept short?<br>**F2 — 日本語:** Transactionを短くすべきなのはなぜですか？ | **A1:** 違います。ACID Consistencyはconstraintやbusiness invariantをtransaction前後で守ること、CAP Consistencyはpartition中も全nodeが単一の最新値のように振る舞うことです。<br>**Example / 例:** 残高非負constraintはACID、別regionから最新残高を同時に読む保証はCAP側の議論です。<br>**Keywords:** ACID consistency, CAP consistency, invariant, linearizability<br><br>**A2:** 長いtransactionはlock、connection、old row versionを保持し、contentionとcleanup costを増やします。User inputやremote callを待たず必要なdatabase operationだけを含めます。<br>**Example / 例:** Payment API応答を待つ間database row lockを保持しません。<br>**Keywords:** short transaction, lock duration, connection, contention |
